# Needs Validation

These are source-grounded leads whose decisive fact lies outside source and the local sandbox. They carry no severity and are not confirmed vulnerabilities.

## A crafted .apkg expands without limit into the app cache, and a failed extraction leaves the partial file behind

`ApkgReader.read:unbounded-collection-extraction-without-cleanup` — boundary: Zip entry filter and import size limits

ApkgReader.read (ApkgReader.kt:47-63) streams any zip entry whose basename is collection.anki21 or collection.anki2 into context.cacheDir/apkg_import with zip.copyTo. Nothing limits the compressed or decompressed size. The 20 MB MAX_BYTES cap in ImportRepository.load (line 85) applies only to the CSV/TSV branch. Deflate expands about 1000:1, so an Anki deck of about 20 MB can expand to about 20 GB of zeros. The only workDir cleanup (line 74) is in a finally that starts after SQLiteDatabase.openDatabase (line 69). Any exception thrown during extraction, or a process kill during it, therefore leaves the partial file behind. A deliberately truncated deflate stream is not needed for this. A well-formed entry larger than the device's free space ends in an IOException (ENOSPC) inside the loop, so the leftover file is as large as all the free space that was available. ImportScreen.kt:71 shows this only as 'Dosya okunamadı'. The extraction runs on the main dispatcher (rememberCoroutineScope, and load has no withContext(IO)), so a user who picks 'Close app' at the ANR prompt also leaves the file. The leftover sits at a fixed name. The next import of the same name overwrites it, and a later successful .apkg import deletes it. At most two files remain (collection.anki21 and collection.anki2). The only way in is the learner choosing the file in the OpenDocument picker. No exported intent filter accepts .apkg. Local evidence comes from Java transcriptions of the loop. h-import: 8309 bytes became 8 MiB with no check, and a truncated 6231-byte input left 6.35 MB. v3-01: a well-formed 65390-byte zip that expands to 64 MiB hit 'No space left on device' at about 16 MiB and left a 16773120-byte collection.anki21. A second import overwrote it with 1 MiB. The impact on other apps or the OS, and how long it lasts, depends on Android cache reclamation and reserved space. That is not observable here.

**Claimed root cause:** The extraction loop (ApkgReader.kt:47-63) has no per-entry or aggregate byte budget, and the .apkg branch of ImportRepository.load (lines 72-73) has no input cap. The workDir cleanup (ApkgReader.kt:72-75) only wraps readCollection after SQLiteDatabase.openDatabase (line 69). Exceptions from extraction (ENOSPC, truncated or corrupt deflate data) or from openDatabase, and process death, all skip it. The resulting partial file stays in cacheDir/apkg_import.

### Trace
1. `LexiFlow/app/src/main/java/com/lexiflow/ui/screens/ImportScreen.kt:74` (entrypoint, ImportScreen picker) — The learner picks an attacker-authored .apkg with ActivityResultContracts.OpenDocument (launched with '*/*' at line 90). open(uri) calls container.importer.load(uri) at line 67 inside rememberCoroutineScope (main dispatcher). This picker is the only path to the importer. The manifest has no intent filter for .apkg.
2. `LexiFlow/app/src/main/java/com/lexiflow/data/repo/ImportRepository.kt:73` (propagation, ImportRepository.load) — A display name ending in .apkg or .colpkg (line 72) passes the content stream straight to ApkgReader.read(stream, File(cacheDir, 'apkg_import')) with no size check. MAX_BYTES at line 85 applies only to the CSV branch.
3. `LexiFlow/app/src/main/java/com/lexiflow/data/importer/ApkgReader.kt:52` (propagation, ApkgReader.read extraction loop) — Any entry whose basename (line 50) is collection.anki21 or collection.anki2 is selected, whatever its declared or actual size.
4. `LexiFlow/app/src/main/java/com/lexiflow/data/importer/ApkgReader.kt:54` (sink, ApkgReader.read extraction loop) — zip.copyTo writes the fully decompressed stream to cacheDir/apkg_import/<fixed name> with no byte budget, until the stream ends or the write fails with ENOSPC. Any exception here propagates out of read() before the try/finally at lines 70-75, so the cleanup at line 74 never runs.

### Evidence
- `LexiFlow/app/src/main/java/com/lexiflow/data/importer/ApkgReader.kt:74` — The only workDir cleanup is in a finally that is entered only after SQLiteDatabase.openDatabase succeeds at line 69. Extraction and open failures are outside it.

### Blockers
- No Android runtime in the sandbox, so ApkgReader cannot be run as target bytecode. Both local results (agents/h-import/artifacts/evidence-1.txt, and agents/v3-01/artifacts/evidence-1.txt once the parent promotes it) are Java transcriptions of ApkgReader.kt:47-63. Regression test: an entry over a fixed budget (for example 200 MiB of decompressed bytes, counted inside a bounded copy loop) must raise an import error and leave workDir empty. The same test must cover a truncated deflate stream and a non-SQLite collection file, which means the cleanup has to wrap extraction and openDatabase.

## One oversized CSV cell is stored in a words row that the deck, word, edit and search screens (and, for pos/ipa, the study and lock-screen queries) may then be unable to read, edit or delete

`DelimitedParser.toCandidates:unbounded-cell-length-persisted-to-word-row` — boundary: Delimited parser and transcript caps

The CSV/TSV import caps only the whole file (20 MiB, ImportRepository.kt:85) and the word column (120 chars, DelimitedImport.kt:206). Notes, tags, POS, IPA and example cells have no length bound. An example that does not contain the word is moved into notes as "Örnek: <example>" (ImportRepository.kt:138-139, 148). Apkg rows go through the same toCandidates path. These values are written unchanged to words.notes, tags, pos and ipaUs (WordRepository.kt:79-83). The import's read-back (ImportRepository.kt:155) reads only senses, so a multi-MB notes, tags, pos or ipa value commits. Every per-word UI read of that row afterwards is a SELECT * FROM words: the deck word list (Daos.kt:94 via DeckScreens.kt:101), word detail (Daos.kt:83 via DeckScreens.kt:135), the delete action (WordRepository.deleteWord reads the row first, line 124), the word edit screen (DeckScreens.kt:240, so the field cannot be shortened), the search on the decks screen (Daos.kt:95) and, if a tag contains 'wordbook', the Wordbook screen (Daos.kt:96). Lookups by lemma also load the full row through WordDao.byLemmaKey (Daos.kt:99). These are a later import of the same lemma with a different meaning (ImportRepository.kt:144), a bot battle round when the lemma is in the built-in WordBank (MiscRepositories.kt:168) and a cultural-context card lookup for that lemma (MiscRepositories.kt:74). The card-detail projection (CARD_DETAIL_SELECT, Daos.kt:41-45) also selects w.pos and w.ipaUs, but not notes or tags. So an oversized pos or ipa value would also be loaded by the review and new-card queues, lock-screen question generation, the widget, stats, story and speaking queries (Daos.kt:115-133; for example ReviewScreens.kt:93, StudyRepository.kt:47/51, LockScreenRepository.kt:123/131-135). An oversized notes or tags value reaches only the per-word screens and lemma lookups above. The main deck list (Daos.kt:57-67) does not select word columns, so the deck overview itself still loads. No UI path deletes or archives a deck: DeckDao.delete has no caller and nothing sets decks.archived. The suspend action that would remove the card from the study queries exists only on the word detail screen (DeckScreens.kt:192), which loads the row first. On Android, a row larger than the default ~2 MB CursorWindow is expected to fail to load (SQLiteBlobTooBigException on API 28+). None of these collectAsState, LaunchedEffect and repository call sites handles it. So a shared vocabulary file could leave a deck that crashes the app whenever it, the word or a matching search is opened, and, for a pos or ipa payload, whenever a study, review or lock-screen query selects that card. The user cannot delete, edit or suspend the word from the UI. The only recovery would be clearing app data, which loses the local learning DB. The impact stays on the importing learner's own device and needs that learner to import the file. Verifier v3-02 independently ran the real core.jar parser on a 12582966-byte CSV: 3 MiB notes, POS, IPA and example cells all came back unchanged, as 1 candidate with 0 errors.

**Claimed root cause:** DelimitedParser.toCandidates (DelimitedImport.kt:191-224) and ImportRepository.import (ImportRepository.kt:116-157) apply no per-field length limit to notes, tags, pos, ipa or example. The only limits are word <= 120 and the 20 MiB whole-file cap, so one row can be persisted larger than the platform's per-row cursor read limit. All later reads of that row have no error handling. They are SELECT * FROM words by id, deck, search or lemma key (list, detail, edit, delete, search, lemma lookups) or, for pos/ipaUs, the CARD_DETAIL_SELECT projection.

### Trace
1. `LexiFlow/app/src/main/java/com/lexiflow/data/repo/ImportRepository.kt:84` (entrypoint, ImportRepository.load) — A CSV/TSV the learner picks through OpenDocument (ImportScreen.kt:67/74) and that an attacker wrote is read in full. 2. `LexiFlow/core/src/main/kotlin/com/lexiflow/core/importer/DelimitedImport.kt:206` (propagation, DelimitedParser.toCandidates) — The only per-field check is word.length > 120. Notes (214), tags (215), pos (216), ipa (217) and example (212) are taken with no length limit.

The read-back at line 155 reads only senses, so the transaction commits.
4. `LexiFlow/app/src/main/java/com/lexiflow/data/repo/WordRepository.kt:82` (propagation, WordRepository.insertWord) — WordEntity.notes (82), tags (83), pos and ipaUs (79) are stored as given.

## Exported MainActivity lets NavController.handleDeepLink act on caller intent extras, bypassing the lexiflow:// allowlist and the onboarding gate

`LexiFlow/app/MainActivity:navcontroller-intent-deeplink-extras-bypass-router` — boundary: Deep-link router after onboarding

MainActivity is exported (AndroidManifest.xml:32). The app's own router, LexiFlowRoot.handleDeepLink (LexiFlowRoot.kt:163-169), accepts only lockquestion/*, review and speaking, and the LaunchedEffect at lines 154-157 runs it only after onboarding. But LexiFlowRoot.kt:95 creates an activity-bound NavHostController with rememberNavController(), and the NavHost at line 121 sets the graph. In androidx.navigation 2.8.5 (libs.versions.toml:9), NavController.onGraphCreated calls handleDeepLink(activity.getIntent()) when deepLinkHandled is false. That method reads the caller-controlled extras android-support-nav:controller:deepLinkIds (int[]), deepLinkArgs (ArrayList<Bundle>) and deepLinkExtras (Bundle). It checks only that each id exists in the graph (the first must equal the graph id), then navigates there with those arguments. Nothing checks the caller or the onboarding state. So any installed app, with no permissions, can send an explicit intent to com.lexiflow.app/com.lexiflow.MainActivity and open any composable destination with arguments it chooses. Destination ids are ("android-app://androidx.navigation/" + route).hashCode(), not route.hashCode() as the hunter wrote. For a route-less compose NavHost the graph id is expected to be 0. The source-visible effects when a destination opens are small:
- drill/{mode} with an invalid mode string makes StudyMode.valueOf throw. With no mode argument at all, the !! on a null argument throws instead (the same happens for lockquestion/{id} and culture/{kind}). Either way the app crashes, but only for that launch.
- lockquestion/new runs LockScreenRepository.createQuestion. It inserts a lock-screen question, marks an example as shown, and bumps lockQuestionCounter and lastLockQuestionAt. After onboarding, the intended lexiflow://lockquestion/new route can already do this. The bypass adds only the pre-onboarding reach.
- cultureitem/{id} calls culture.markShown for an existing context id.
Every other destination needs a user tap before it changes anything, and the battle screen does not connect when it opens. The Android runtime is not available, so the end-to-end navigation has not been observed.

**Claimed root cause:** The app relies on its own allowlisting deep-link router, but it hosts an activity-bound NavController inside an exported activity and never strips or overrides the NavController's built-in handling of the launch intent. Caller-supplied android-support-nav:controller:* extras therefore form a second, unrestricted router that ignores the allowlist and the onboarding gate.

## Shipped release APK is signed with an AGP debug key that sits world-readable, under the public default password, on an ephemeral cloud dev container

`LexiFlow/app/build.gradle.kts:signingConfigs:release-falls-back-to-debug-key` — boundary: Release signing configuration

When keystore.properties is absent, app/build.gradle.kts quietly signs the release build type with signingConfigs.debug. LexiFlow/dist/LexiFlow-1.0.0.apk is the committed release build, and README.md:13-19 tells end users to sideload it. An independent parse of its APK Signing Block shows a single v2 signer. There is no v1 JAR signature and no v3 or v3.1 block, so the APK carries no key-rotation lineage. The signer's certificate is CN=Android Debug, O=Android, C=US, serial 1, 2048-bit RSA, SHA-256 0935d68a49af26740ab3818b2f2d3ef7b0190f4ab24dbbd1527dc9dba80aaf2d, notBefore 2026-10-18 15:48:01 UTC. The verifier then listed /root/.android/debug.keystore on the audit host with a trusted, read-only keytool call. Its androiddebugkey entry has exactly that SHA-256, and the file's mtime is the same second as the certificate's notBefore. So the private key behind the update identity of every install of this APK is a PKCS12 file with mode 0644 at the standard AGP path, protected only by the public password 'android' and alias 'androiddebugkey'. It sits on a short-lived cloud session container (FINAL_IMPLEMENTATION_REPORT.md:25 says the APKs were produced 'in this session'), not in custody-controlled key storage. Android installs a later APK for com.lexiflow.app signed with the same certificate as an in-place update. That update inherits the app's private data, including the plaintext JWT in DataStore and the learning database. Two further consequences follow. Anyone who copies the key from this container or a snapshot of it can ship such an update. The owner can no longer ship same-identity updates once the container is recycled. Moving to a real key without rotation lineage forces users to uninstall. ## Registration rate limit becomes one global bucket behind the recommended reverse proxy

`lexiflow-backend-register-ratelimit-keyed-on-proxy-peer` — boundary: Environment precedence and secret defaults

The anonymous POST /v1/auth/register route is wrapped in RATE_LIMIT_REGISTER, which allows 10 requests per 60 s. Its bucket key is call.request.origin.remoteHost. The server installs no XForwardedHeaders or ForwardedHeaders plugin and has no trusted-proxy setting, so the key is always the immediate TCP peer and forwarded headers are ignored. The backend README (line 108) tells operators to run the server behind a TLS reverse proxy. In that topology every client reaches Netty from the proxy's address. One anonymous client sending 10 registrations a minute would then get 429 rate_limited returned to every other new user of the instance, which blocks account creation and therefore all online features for newcomers. I reproduced the mechanism independently in the sandbox with a simulated proxy. A real client sent 10 registrations through a loopback relay that forwards the client address in X-Forwarded-For, X-Real-IP and Forwarded, and all 10 got 201. A different real client's first request through the same relay then got 429. Direct peers kept separate buckets: A got 429 on its 11th request while B and E got 201. ## Unthrottled full-table leaderboard aggregation can tie up the shared 10-connection pool used by JWT auth and result persistence

`lexiflow-backend:leaderboard-unbounded-aggregation-shared-hikari-pool` — boundary: Shared HikariCP pool (10 connections) used by leaderboard and JWT validateUser

In Postgres mode, which the shipped docker-compose.yml uses through DATABASE_URL, any registered player can call GET /v1/leaderboard as often and as concurrently as they like. Registration is free and limited only to 10 per minute per IP. The route has no rate limit, no in-flight bound and no cache. Each call first uses one pooled connection for the JWT validateUser -> findUser check. It then takes a second connection and runs a JOIN users + GROUP BY player_id + ORDER BY aggregates over every battle_results row, or every row of one mode, before LIMIT 50. No statement or query timeout is set in code or in compose. The connection is held for the whole query. The pool is a single HikariCP pool with maximumPoolSize=10 and connectionTimeout=10 s. It also serves findUser for every authenticated HTTP request and WebSocket upgrade, BattleManager.saveBattleResults and saveReport. battle_results grows by one row per player per finished room and is never pruned. Attacker-run accounts can grow it: four queued accounts start a room at once, and the room finishes as soon as all of them submit. At 2 messages per round and 20 messages per 10 s per connection, that is about one row per account per second. If per-query time reaches the order of seconds, about 10 concurrent leaderboard calls can hold every connection. Other users' authentication would then wait 10 s and fail with HTTP 500 (the StatusPages Throwable handler). saveBattleResults failures are only logged, so those finished-battle results would be permanently missing from the leaderboard. Whether production query latency reaches that range has not been measured.

**Claimed root cause:** The leaderboard route has no per-subject or global rate limit, in-flight bound or cache. Its SQL cost is O(rows in battle_results): the explicit indexes are on mode and player_id, and the implicit ones are the primary key and UNIQUE(room_id, player_id). None of them can serve the aggregate ORDER BY. There is no statement timeout. The query runs on the same single, unpartitioned 10-connection Hikari pool as authentication (findUser) and battle-result and report writes. Attacker-paced read work can therefore starve other principals' authentication and leaderboard integrity.

### Trace
1. `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/LeaderboardRoutes.kt:12` (entrypoint, Route.leaderboardRoutes) — GET /v1/leaderboard. It needs only a valid JWT for an existing user. mode is an optional enum; the absence of mode gives the all-modes, whole-table aggregation.

`template-parts:carbon_get_theme_option:unescaped-theme-option-echo` — boundary: Admin-controlled option escaping

functions.php registers a Carbon Fields theme_options container with free-text fields hero_title, hero_subtitle, about_title, tokenomics_title, join_title and join_subtitle (functions.php:47,49,54,71,87,89). index.php is the theme's only page template, and on every front-end request it includes the hero, about, tokenomics and join template parts (index.php:14-17).
