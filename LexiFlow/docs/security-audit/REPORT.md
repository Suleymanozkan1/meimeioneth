## 2. Security posture summary

LexiFlow's core boundaries hold up well under source review and local testing: JWT verification pins HS256/issuer/audience/expiry and rejects `alg:none`, foreign keys and unknown subjects; battle-room actions are authorized per message with atomic deadline/submit handling; SQL is parameterised; request/frame sizes are capped; model output is decoded into typed contracts and rendered only as plain text; Android components other than `MainActivity` are not exported and PendingIntents are explicit. The confirmed problems are at the edges: a committed example JWT secret that the server accepts, operator AI spend that scales with free identities, leaderboard integrity, a staff-name filter bypass, and a token-in-URL log leak at TRACE. Several further leads (lock-screen privacy, deep-link extras, import resource limits, release signing, the theme packager, proxy-keyed rate limits, DB pool starvation) need a device, deployment or owner check to settle.

## 4. Confirmed finding details

### 4.1 Committed .env.example JWT_SECRET placeholder is accepted as the production signing key, allowing forged tokens for any existing player — MEDIUM

- **Fingerprint:** `lexiflow-backend-env-example-jwt-secret-placeholder-accepted`
- **Source location:** `LexiFlow/backend/.env.example:9` → `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/BattleRoutes.kt:31`
- **Lower-trust principal:** Unauthenticated network client who has read the public repository, against a LexiFlow backend deployed with the .env.example JWT_SECRET left in place.
- **Root cause:** Config.fromEnv treats any provided JWT_SECRET of length >= 32 as acceptable and does not reject the publicly committed .env.example placeholder or other low-entropy values. The example file also ships a value that passes validation. An empty value would instead fall back to a random per-process secret.
- **Conditions:** [system_configuration] The operator follows the documented `cp .env.example .env` path and leaves the JWT_SECRET line unchanged, despite the 'replace the placeholders' comments in .env.example line 1, docker-compose.yml line 2 and README line 22. Nothing at startup flags it.; [data_state] The victim's playerId is known and the victim exists in the store. Ids are returned by GET /v1/leaderboard and in round_result PlayerResult entries to co-players. Tokens for nonexistent subjects are rejected.; [authentication_level] None beyond the public repository contents and network reach to the server. To read leaderboard ids, an attacker can also register a free account.
- **Bounded reproduction (target-native):** Inside tools/sandbox.sh (loopback only, 2 GiB, 256 pids, CPU 120 s), call AppConfig.Companion.fromEnv(Map.of("JWT_SECRET", <placeholder>)) and observe that it returns without throwing and with jwtSecretGenerated=false. Start the real server main com.lexiflow.server.ApplicationKt from /opt/lexiflow-audit-cp with env -i JWT_SECRET=<placeholder> PORT=18081 AI_PROVIDER=none (in-memory store). POST /v1/auth/register {"displayName":"Victim"} and read playerId. Sign three tokens with name=Mallory: a control token with a different secret and sub=victim, a forged token with the placeholder and sub=victim, and a forged token with the placeholder and a nonexistent sub. Call GET /v1/leaderboard with each token. Then open /v1/battle with the forged token and read the first frame, and attempt the same with the control token.
- **Actual result:** fromEnv(placeholder) gave jwtSecretGenerated=false. fromEnv rejected a 31-character value and accepted 32 x 'a'. The server log showed 'Starting LexiFlow server: port=18081, db=memory, ai=none, aiRateLimit=20/min, jwtSecret=provided' and no JWT warning. Registering Victim returned 201 with playerId=a8855df0-c18d-4b75-b498-89f62b6fe1e2. On /v1/leaderboard: control token -> 401; placeholder-forged token for the victim -> 200; placeholder-forged token for a nonexistent sub -> 401. The WebSocket first frame for the forged token was {"type":"welcome","playerId":"a8855df0-c18d-4b75-b498-89f62b6fe1e2","displayName":"Mallory","onlinePlayers":1}. The control-token WebSocket handshake was refused. Not exercised: the AI routes (AI_PROVIDER=none) and full battle submit/report as the victim. Those effects come from source only.
- **Impact / priority:** likelihood low (An operator has to skip replacing one placeholder line after the documented copy step, even though three comments tell them to replace it. When they do skip it, nothing stops or warns them: the server logs jwtSecret=provided, and compose guards only that DB_PASSWORD is present.); impact medium (Full impersonation of any existing player across all authenticated APIs: battle as the victim, file reports as the victim, earn or lose wins, and use up the victim's AI rate-limit quota. It also allows an unvalidated display name that is broadcast to co-players and stored in battle results. There are no admin roles, no cross-player data beyond game state, and no way to create new identities through this path.)
- **Smallest fix:** Stop shipping a secret value that passes validation. Leave JWT_SECRET empty in .env.example, which makes the server generate a random secret and log a warning. In Config.fromEnv, reject known placeholders and obviously low-entropy values. Optionally add a compose guard (e.g. JWT_SECRET: ${JWT_SECRET:?Set JWT_SECRET}) together with the code check. Regression test: AppConfig.fromEnv(mapOf("JWT_SECRET" to "replace-with-a-long-random-secret-at-least-32-chars")) must throw, and so must fromEnv(mapOf("JWT_SECRET" to "a".repeat(32))).

### 4.2 Operator-paid AI budget escapes the per-player limit through free, unlimited identity minting — MEDIUM

- **Fingerprint:** `lexiflow-backend:RATE_LIMIT_AI:per-subject-quota-escape-via-free-registration`
- **Source location:** `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/PublicRoutes.kt:34` → `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/ai/AnthropicProvider.kt:86`
- **Lower-trust principal:** Anonymous internet client with no prior account, scripting plain HTTP requests from a single source address.
- **Root cause:** RATE_LIMIT_AI accounts on call.principal<JWTPrincipal>().subject (Application.kt line 155), a dimension the attacker can mint for free via /v1/auth/register (PublicRoutes.kt lines 35-41, JwtService 90-day TTL). No aggregate limit (per source, global or daily) caps the sum across subjects, and upstream attempts (up to 2 billed provider.complete calls per counted request) are not counted against the budget.
- **Conditions:** [system_configuration] AI_PROVIDER=anthropic with ANTHROPIC_API_KEY set (the default is none, under which AI routes return 503).; [authentication_level] None beyond self-service anonymous registration; any internet client can mint tokens.; [network_routing] Per-IP registration rate applies when the server sees client IPs directly (compose publishes 8080). Behind a reverse proxy without forwarded-header handling, registration is limited globally at 10/min, which still yields 14,400 new full-budget identities per day. Additional source IPs (e.g. IPv6) multiply the per-IP figure.; [third_party_dependency] Actual monetary loss depends on the operator's provider spend limits outside the repository. If a provider-side cap exists, the same path instead exhausts it and denies AI to all players. Either outcome is a meaningful shared effect; the quota-escape mechanism itself is fully source-proven and does not depend on any unknown deployed control.
- **Bounded reproduction (target-native):** Inside tools/sandbox.sh (loopback-only netns, mem 2 GiB, pids 256, CPU 120 s, wall<=300 s), start a Python stub on 127.0.0.1:19011 that answers /v1/messages with a valid enrich JSON and counts hits. Start com.lexiflow.server.ApplicationKt from /opt/lexiflow-audit-cp with PORT=18090, JWT_SECRET of 40 'x', AI_PROVIDER=anthropic, ANTHROPIC_API_KEY=dummy-not-a-real-key, ANTHROPIC_BASE_URL=http://127.0.0.1:19011, ANTHROPIC_FALLBACKS=off, and no DATABASE_URL. Register several identities from 127.0.0.1, then send 21 enrich calls with each of 3 tokens, recording statuses and stub hit counts.
- **Actual result:** Independently reproduced by verifier v3-12 (evidence-1.txt): from one source IP, 6 registrations returned 201 x6 (6<10/min register limit). Each of 3 identities got 200 x20 and 429 x1 on /v1/ai/enrich, i.e. 60 billed upstream stub hits from one source in under a minute against a 20/min per-subject limit, using only 3 of the free identities minted that minute. Matches hunter h-spend evidence-1. Hunter h-spend evidence-2 separately showed up to 2 billed provider calls per counted request (corrective retry) and 3 upstream calls per request when the upstream always errors (maxRetries), a bounded contributing multiplier.
- **Impact / priority:** likelihood high (Anonymous, scriptable with plain HTTP, needs no special timing, and works from a single source address whenever AI is enabled.); impact medium (Unbounded growth of operator-paid model spend, or exhaustion of the operator's shared provider quota (single ANTHROPIC_API_KEY) that denies AI to all players. No data compromise or code execution.)
- **Smallest fix:** Add aggregate accounting that new identities cannot reset. Use an operator-configured global AI ceiling and a per-source (trusted client IP) AI budget, layered over the existing per-subject RATE_LIMIT_AI bucket. Count every upstream provider attempt, including the corrective retry and the HTTP retries, against the global ceiling. Do NOT implement the extra limits as nested rateLimit(...) blocks. In Ktor 3.0.3, Route.rateLimit installs the route-scoped RateLimitInterceptors with a single provider name. Core's addAllInterceptors runs a route-scoped interceptor only when findPluginInRoute(call.route) returns that same instance, which is the innermost one, so outer nested limiters are silently skipped. Enforce the extra budgets in one explicit guard instead. Optionally add a persisted daily per-subject quota and a minimum account age or activity before AI access. Make the registration limit configurable and keyed on a trusted forwarded client address behind proxies. Bound or evict the per-source map.

### 4.3 Battle WebSocket JWT carried in the ?token= query string is written to server logs by Ktor TRACE loggers — LOW

- **Fingerprint:** `LexiFlow/backend/Application.kt:AUTH_JWT_WS:query-token-in-uri-logged`
- **Source location:** `LexiFlow/app/src/main/java/com/lexiflow/data/remote/BackendClient.kt:112` → `LexiFlow/backend/src/main/resources/logback.xml:7`
- **Lower-trust principal:** A reader of the server's log output who has no access to JWT_SECRET or to players' devices.
- **Root cause:** The JWT is sent as a URL query parameter. The client builds it at BackendClient.kt:112 and sets no header at BattleSocket.kt:28. The server's AUTH_JWT_WS authHeader reads it first, at Application.kt:143-145. Redaction is done only in the custom CallLogging format. Framework loggers that print call.request.uri stay under the uncapped root level `${LOG_LEVEL:-INFO}` (logback.xml:7).
- **Conditions:** [system_configuration] The operator runs the server with LOG_LEVEL=TRACE, a documented value. At DEBUG and at the INFO default, no token was logged.; [authorization_role] The attacker can read the server's stdout or log pipeline but does not hold JWT_SECRET.; [user_interaction] A victim opens an online battle connection while TRACE logging is on. The app always uses the query transport.
- **Bounded reproduction (target-native):** Inside the sandbox, start java -cp '/opt/lexiflow-audit-cp/*' com.lexiflow.server.ApplicationKt with the dummy env above and stdout redirected to a log file, once per LOG_LEVEL value. Register a dummy player over loopback. Perform a WebSocket upgrade to /v1/battle?token=<issued JWT>, as BackendClient.battleSocketUrl builds it. Then perform the same upgrade using the Authorization header instead. Count the server log lines that contain the full issued JWT, for each level.
- **Actual result:** Both transports returned 101 Switching Protocols at every level. At TRACE, 4 log lines contained the full issued JWT, all for the ?token= connection: io.ktor.server.auth.Authentication 'Trying to authenticate /v1/battle?token=eyJ...' and 'Authentication succeeded for /v1/battle?token=eyJ...', StatusPages 'No handler found for status code 101 ... for call: /v1/battle?token=eyJ...', and io.ktor.server.websocket.WebSockets 'Starting websocket session for /v1/battle?token=eyJ...'. The header-transport connection logged no token and no 'Bearer' string. CallLogging logged only '101 GET /v1/battle'. At DEBUG and at INFO, 0 lines contained the token.
- **Impact / priority:** likelihood low (It requires the operator to set LOG_LEVEL=TRACE, which is documented but not the default, and an attacker with log read access but without JWT_SECRET. Both are plausible during debugging, but neither holds by default.); impact low (The impact is impersonation of pseudonymous player accounts (battle submissions and reports, leaderboard standing, the victim's AI rate-limit bucket) for up to 90 days with no revocation. No operator secret or API key is exposed.)
- **Smallest fix:** Stop sending the battle JWT in the URL. The app sets an Authorization: Bearer header on the OkHttp WebSocket request, and the server's AUTH_JWT_WS provider drops the queryParameters fallback, or keeps it only behind an explicit compatibility flag during migration. The header transport was verified locally to authenticate (101) without logging the token at TRACE. As defence in depth, cap the Ktor loggers that print request URIs at INFO in logback.xml. Regression tests: a BattleTest case asserting that ?token= alone returns 401 and the header returns 101, and a TRACE log-capture test asserting that no logged line contains the issued token.

### 4.4 Public battle leaderboard can be farmed by matching one operator's free accounts against each other — LOW

- **Fingerprint:** `LexiFlow/backend/battle/BattleManager.finishRoom:self-match-win-farming`
- **Source location:** `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/PublicRoutes.kt:39` → `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/LeaderboardRoutes.kt:18`
- **Lower-trust principal:** A registered player who controls a second (or third and fourth) free account and wants the top leaderboard position without real competition.
- **Root cause:** BattleManager.finishRoom sets won = index == 0 && r.submitted for every room composition (BattleManager.kt:274). Matchmaking dedupes only the same playerId (BattleManager.kt:133). Rooms start after the 3 s window with 2+ players (:161-167) or immediately with 4 (:158-159), and finish as soon as all members submit any non-blank text (:231-236, :242). Neither store applies an opponent-independence, pair-repetition, opponent-participation/quality or account-age condition when it aggregates wins (InMemoryStore.kt:37; PostgresStore.kt:98, 104), and rankLeaderboard orders by wins first (Store.kt:62). Identities are free (PublicRoutes.kt:39-41).
- **Conditions:** [authentication_level] The attacker self-registers two or more anonymous accounts (free, 10/min per TCP peer) and opens one battle WebSocket per account.; [data_state] An honest player who joins the same mode queue in the same match window could take a slot in the room. That only adds noise. A 4-account self-filled room starts instantly and leaves no window.
- **Bounded reproduction (target-native):** Inside tools/sandbox.sh (loopback only, 2 GiB, CPU 120 s), run the in-process harness: java -cp '/opt/lexiflow-audit-cp/*' V308.java. It builds BattleManager(InMemoryStore, BattleSettings(null,3000,3000,4,20,10000,3,600000)), which are the production defaults, and drives it through BattleManager.handle(conn, ClientMessage). Create dummy users honest-a, honest-b, operator-main and operator-alt, and connect one PlayerConnection for each. Play one honest 2-player round: honest-a submits a full sentence using the drawn words, and honest-b submits 'I like it very much'. Repeat 4 times: operator-main and operator-alt send join_queue, wait for match_found (3 s window), operator-main submits a sentence with all drawn words, operator-alt submits '.', then wait for round_result. Call store.leaderboard(FIVE_WORD_SENTENCE, 50).
- **Actual result:** Every operator room held exactly [operator-main, operator-alt]. operator-main ranked first each time (overall 81-83 vs 40). 4 rounds took 12067 ms. Leaderboard: rank 1 operator-main wins=4 games=4 averageScore=82.0; rank 2 honest-a wins=1 games=1 averageScore=83.0; operator-alt wins=0. The farmed account outranks the honest winner even though the honest winner has a higher average. This matches the hunters' independent runs: 6 wins in 18.2 s over the real Ktor WebSocket server, and 5 wins in 27 ms with 4 self-filled accounts.
- **Impact / priority:** likelihood medium (It needs only free self-registration and two to four WebSocket connections running a trivial script, with no special timing. The per-socket and registration rate limits still allow roughly one win every 1-3 s.); impact low (It harms the integrity of a shared, cosmetic ranking that the architecture lists as a protected resource. The attacker's chosen name takes rank #1 and honest players are pushed down. There is no data disclosure, privilege change or effect on other accounts.)
- **Smallest fix:** Credit a leaderboard win only when the round reflects independent competition. Require at least one opponent submission that clears a minimum score or taskCompletion threshold. Cap or deduplicate credited wins per opponent set (unordered pair or room roster) per day. Prefer ranking on distinct defeated opponents or an Elo/Glicko rating over raw win count, and optionally require a minimum account age or a minimum number of distinct opponents before an account is listed. Add a regression test where a fixed pair of accounts plays N consecutive rounds: the credited wins stay at the cap, and an honest player with real wins still ranks.

### 4.5 Staff-impersonation name block bypassed with Turkish letters and diacritics (Admın, ADMİN, Lexıflow, Ädmin) — LOW

- **Fingerprint:** `lexiflow/backend/displayname-reserved-check-missing-turkish-fold`
- **Source location:** `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/PublicRoutes.kt:35` → `LexiFlow/backend/src/main/kotlin/com/lexiflow/server/routes/PublicRoutes.kt:41`
- **Lower-trust principal:** Anonymous internet client registering a display name that other players will read as a LexiFlow staff, admin or moderator account.
- **Root cause:** In isBlocked (DisplayNameValidator.kt:45-54), the reserved-word test on line 51 is words.any { it in reserved || deLeet(it) in reserved }. Here words are only lowercase(Locale.ROOT) splits (lines 46-47). foldTurkish (line 50, defined at lines 63-64) and the compact form are used only for blockedSubstrings (line 53). No NFKD or combining-mark removal is done anywhere. So any reserved word with a Turkish or accented letter, or split across separators, fails the exact set membership test.
- **Conditions:** [authentication_level] None. POST /v1/auth/register is anonymous and rate limited to 10/min per TCP peer.; [user_interaction] The impact depends on other players reading a staff-looking name (in match_found, round_result or the leaderboard) as an official account.
- **Bounded reproduction (target-native):** Run inside tools/sandbox.sh (loopback only). Start java -cp '/opt/lexiflow-audit-cp/*' com.lexiflow.server.ApplicationKt with JWT_SECRET set to 40 dummy 'x' characters, AI_PROVIDER=none and PORT=18081, using the in-memory store (no DATABASE_URL). Wait for GET /health to answer, then POST /v1/auth/register with Content-Type application/json. Send the ASCII controls first (Admin, admin, LexiFlow, Moderator, System, Support, Staff, Adm1n), then the variants (Admın, ADMİN, Lexıflow, LEXİFLOW, Moderatör, Sıstem, Stäff, Ädmin, 'Destek Admın', 'Lexi Flow', Ad-min, 'LexıFlow Destek'). Pause 61 s after every 10 requests, because the register limit is 10/min per TCP peer and rejected requests also count. Compare each response's HTTP status, the error code or echoed displayName, and whether a token is present.
- **Actual result:** All ASCII controls (Admin, admin, LexiFlow, Moderator, System, Support, Staff, Adm1n, 'Supp0rt Staff', 'Admin Destek') got HTTP 400 invalid_display_name. Admın (U+0131), ADMİN (U+0130), Lexıflow, LEXİFLOW, Moderatör, Sıstem, Stäff, Ädmin, 'Destek Admın', 'Lexi Flow', Ad-min and 'LexıFlow Destek' each got HTTP 201, with the name echoed back and a token issued (agents/v3-14/artifacts/evidence-1.txt; this matches the hunter's agents/h-wild/artifacts/evidence-2.txt).
- **Impact / priority:** likelihood medium (One anonymous request with a single native Turkish keyboard character is enough. No account, privilege or race is needed. The register rate limit only slows bulk creation.); impact low (Cosmetic impersonation: a staff-looking name shown to co-players in battle messages and on the public leaderboard. It grants no privilege and exposes no data, but it defeats the anti-impersonation control the README promises and can support social engineering inside the game.)
- **Smallest fix:** Canonicalise the name before the reserved comparison only: lowercase(Locale.ROOT), deLeet, NFKD, remove \p{M}, then foldTurkish. Reject when any canonical word, or the canonical letters-only compact name, is a reserved word. Do not route blockedWords through the same folding: canon('göt') = 'got' would reject the currently valid 'I got it', which HttpApiTest asserts is valid. Avoid unbounded substring matching of reserved words, which would reject harmless names such as 'Ecosystem'. Add regression cases for Admın, ADMİN, Lexıflow, Moderatör, Sıstem, Ädmin, 'Lexi Flow' and Ad-min, and keep 'I got it' and 'Klasik Müzik' valid. A mixed-script confusables check (e.g. Cyrillic а) is a possible extra hardening step, not part of this root cause.

## 6. Hardening notes and positive patterns

### Hardening (not findings)

**.apkg archive and SQLite import** (`h-import`)
- ImportRepository.kt:84-85 reads the whole CSV stream with readBytes() before checking MAX_BYTES. Read through a bounded stream (stop at MAX_BYTES+1) so oversized files are rejected without buffering them in memory.
- CultureScreens.kt:85 reads a transcript file with an unbounded readBytes() and no try/catch before take(500_000). Read at most 500_000 chars with a bounded reader and catch IO/Security exceptions (own-process OOM/crash today).
- DelimitedImport.kt:137 cleanCell regex <[^>]+> (and MiscRepositories.kt parseSubtitle, same pattern) is quadratic on unmatched '<' (evidence-3: 32000 chars -> 1.5 s, about 4x per doubling) and runs twice per cell on the main thread. Use a non-backtracking tag stripper or cap the cell length first.
- ImportRepository.load and ImportScreen.open run all import parsing and IO on the Main dispatcher (no withContext(Dispatchers.IO)), and ImportScreen.kt:71 catches only Exception, so an OutOfMemoryError from a crafted file crashes the app.
- ApkgReader.kt:85/96-97: header size comes from attacker-defined note-type fields and every row is padded to it (memory grows as notes x fields), and the opened collection can define 'notes' as a view (for example a recursive CTE). Cap fields per note type, total notes, and query work (for example a progress handler or time budget).
- ApkgReader uses a fixed workDir cacheDir/apkg_import, so two concurrent imports overwrite and delete each other's collection file. Use a unique temp directory per import, removed in a finally that also covers extraction.

**/v1/battle WebSocket token transport** (`h-auth`)
- The register rate limit (and the AI limit's anonymous fallback) is keyed on call.request.origin.remoteHost, and the XForwardedHeaders/ForwardedHeaders plugin is not installed. Behind the reverse proxy the README recommends, all clients share one 10/min registration bucket, which is a nuisance-level denial of registration. Peer-owned AI-quota and register-abuse units may want this.
- Behind the reverse proxy the README recommends, default access-log formats (for example nginx combined $request) would record /v1/battle?token=<JWT>. No proxy config is shipped, so this is not source-visible. Moving the token to the header (see the candidate) removes the issue.
- The verifier accepts an aud array that contains lexiflow-app alongside other values (observed 101), and it does not require exp to be present. Both still require a valid JWT_SECRET signature, so this is not exploitable. Consider requiring exp, and an exact single audience.
- Every self-hosted deployment uses the same constant iss=lexiflow and aud=lexiflow-app. Separation between deployments rests only on distinct JWT_SECRET values. The client already clears serverToken when the backend URL changes (SettingsScreens.kt:163), so it does not replay a token to another server.
- Tokens last 90 days with no revocation, rotation or deny-list. Leaked tokens cannot be invalidated except by rotating JWT_SECRET for all users.

**AI prompt assembly from learner and imported text** (`h-ai`)
- LexiFlow/backend/src/main/kotlin/com/lexiflow/server/ai/Prompts.kt userMessage: the <request> delimiter is not neutralised inside requestJson (LexiJson does not escape '<' or '/'), so learner text can contain a literal '</request>'. Escaping '<' as \u003c in the embedded JSON (or using a per-request random delimiter) would keep the data frame unambiguous. No security boundary depends on this today.
- LexiFlow/backend/src/main/kotlin/com/lexiflow/server/ai/AiService.kt and LexiFlow/core/src/main/kotlin/com/lexiflow/core/ai/AiContracts.kt: validator problem strings echo request values ("target '${t.lemma}' missing", "lemma must be '${request.lemma}'") and decoder exception text, and Prompts.userMessage appends them outside <request> on the corrective retry. SentenceEvaluator.sanitize keeps '\n', so a lemma's newline survives. Returning only fixed problem codes, or JSON-quoting and newline-stripping the echoed values, would keep request data out of the instruction position.
- LexiFlow/core/src/main/kotlin/com/lexiflow/core/ai/AiContracts.kt: device-side re-validation only checks shape, and AI-origin senses/examples are persisted with origin 'AI'. All rendering sinks are plain Compose Text today. Any future WebView, Markdown, autoLink or intent sink for these fields would need its own encoding or sanitising.

**Backend body, frame and provider response sizes** (`h-spend`)
- AnthropicProvider.complete reads provider responses with bodyAsText() and no byte cap (AnthropicProvider.kt line 107). The upstream is operator-configured and output is bounded by max_tokens, but a cap (e.g. 1 MiB) would protect against a misbehaving gateway set in ANTHROPIC_BASE_URL.
- AnthropicProvider retries 408/409/429/5xx up to 2 times per call, honouring retry-after up to 20 s, with no jitter or circuit breaker. AiService adds a corrective retry, so one counted request can make up to 6 upstream attempts (2 billed), with hold times up to about 3x180 s per attempt. Add jitter, a breaker on sustained 429/529, and a global in-flight cap.
- Ktor DefaultRateLimiter refills the full bucket each 60 s window, so a subject can burst about 2x the limit across a window boundary. Per-subject limiter instances accumulate with subject count (cleanup not verified).
- InMemoryStore (used when DATABASE_URL is unset) keeps users, results and reports in unbounded lists. saveBattleResults is O(n) per record, and leaderboard() is O(n) under the same Mutex that findUser takes on every authenticated request, while GET /v1/leaderboard has no rate limit. Cap or index these, or refuse to start AI/battle in memory mode outside dev.
- Whether in-flight AI handler coroutines are cancelled when the client disconnects was not verified on Netty. If they are not, the upstream calls still run and are billed after the client leaves (each is still counted once by the limiter).
- rateLimitRegisterPerMinute is hard-coded to 10 in Config.fromEnv (not configurable), unlike RATE_LIMIT_AI_PER_MINUTE.

**Backend container and environment configuration** (`h-deploy`)
- The root .gitignore has no .env, *.pem or *.key patterns (only *.local). There is no root env consumer today, but add them before the Vite/WordPress tree gains one.
- LexiFlow/.gitignore contains '!debug-shared.keystore', which would force-include a keystore. No such file is tracked; remove the negation so a shared signing key is never committed.
- backend/Dockerfile.dockerignore is honored only by BuildKit. Its comment says context = repository root, while compose uses context LexiFlow/; the '**/' patterns still match. With the legacy builder, `COPY backend ./backend` would copy backend/.env into the build stage. It would not reach the final image, but would sit in local build cache layers.
- docker-compose publishes plain-HTTP 8080 on all interfaces and has no TLS proxy service, while README requires TLS. Consider binding to 127.0.0.1:${HOST_PORT} by default or shipping a proxy service.
- The .env.example DB_PASSWORD placeholder satisfies the compose ':?' guard. The DB is not published, so this has no lower-trust reader, but reject the placeholder too.
- ANTHROPIC_BASE_URL accepts any scheme and host, so the x-api-key could be sent over http. This is operator-controlled only; consider requiring https outside loopback.
- /health discloses whether AI is enabled and the store kind (memory/postgres). This is low-value information, but it lets a scanner see an in-memory deployment.
- Dependency CVE status for ktor 3.0.3, netty 4.1.116.Final, logback 1.5.12, java-jwt 4.4.0 and postgresql 42.7.4 could not be checked offline. Run an owner-side dependency scan.

**Backend module wildcard review** (`h-wild`)
- BattleManager.kt:330 adds (reporter, reported) to room.reports before store.saveReport (line 343). If the save fails, line 349 tells the user 'please try again', but the retry hits the duplicate branch and is dropped silently. Add the pair only after a successful save, or remove it on failure.
- InMemoryStore.kt:22-26 keeps every BattleResultRecord forever and scans the whole list for each inserted record (O(n) per insert, O(n^2) total), and leaderboard (line 28) regroups everything on each call. This only applies when DATABASE_URL is unset, but the README presents it as a runnable server mode. Cap or index it.
- GET /health (PublicRoutes.kt:27-30) tells anonymous clients whether AI is enabled and whether the store is memory or postgres. That is minor fingerprinting; consider limiting it to status.
- The reserved-name check matches whole words only (DisplayNameValidator.kt:51), so 'Lexi Flow', 'Ad-min' and 'Mod_erator' also pass even in ASCII. The remediation for the Turkish-fold candidate should also check the compact form.

**Battle client messages** (`h-battle`)
- GET /v1/leaderboard returns every listed player's playerId (the JWT sub) to any registered user (Store.kt:34-43). It is not a credential, and reporting still requires co-membership, but the field is unnecessary for display and could be omitted or replaced with an opaque per-response handle.
- A 1-character battle submission ("x") scored 56/100 overall in FIVE_WORD_SENTENCE in the local run (evidence-1). Trivial answers raise averageScore on the leaderboard. Consider a hard zero when required targets are missing.
- PostgresStore.leaderboard applies SQL LIMIT before rankLeaderboard's displayName tiebreak, so ties at the 50th position can differ from the in-memory ordering. Ordering consistency only, not a security issue.
- Report snapshots (reports.reported_text) have no retention bound or read/close workflow in source. Define a moderation retention period if a deletion promise is ever made.

**GET /v1/leaderboard in Postgres mode** (`h3-pool`)
- Add a per-subject RateLimit (and ideally a short-TTL cached result) to GET /v1/leaderboard, since its output is identical for all callers.
- Set a Postgres statement_timeout (role level or via the JDBC options parameter) and a Hikari leakDetectionThreshold, or use a separate small pool or materialised table for leaderboard reads, so that auth findUser and battle-result writes cannot be starved by reads.
- Persist the leaderboard as incrementally maintained per-player aggregates (an upsert in saveBattleResults) instead of re-aggregating all of battle_results on each read.
- When saveBattleResults fails (BattleManager.kt:282-286), retry or queue instead of only logging; currently a transient pool timeout permanently loses results.

**Gradle build inputs and release signing** (`h-supply`)
- LexiFlow/gradle/wrapper/gradle-wrapper.properties has no distributionSha256Sum and the repo has no gradle/verification-metadata.xml. Add the official SHA-256 for gradle-8.14.3-bin.zip, compare the committed gradle-wrapper.jar (sha256 7d3a4ac4de1c32b59bc6a4eb8ecb8e612ccd0cf1ae1e99f66902da64df296172) against Gradle's published wrapper checksum, and enable dependency verification.
- LexiFlow/app/build.gradle.kts:44: make assembleRelease fail when keystore.properties is missing instead of falling back to the debug key. Sign with v3 so a key-rotation lineage exists.
- LexiFlow/dist/LexiFlow-1.0.0.apk is a committed binary with no recorded checksum or provenance tying it to a source commit. Publish its SHA-256 and signing-cert fingerprint alongside it.
- LexiFlow/backend/Dockerfile and docker-compose.yml use mutable base-image tags (eclipse-temurin:21-jdk-jammy, eclipse-temurin:21-jre-jammy, postgres:16-alpine). Pin them by digest.
- Runtime classpath versions (logback 1.5.12, Netty 4.1.116.Final via Ktor 3.0.3, postgresql 42.7.4) predate later upstream security fixes. The logback CVE-2024-12798 and CVE-2024-12801 require attacker-controlled logback config, and no reachable Netty or pgjdbc issue was established offline. Upgrade Ktor, Netty and logback and run a dependency scanner.
- build-theme.php: switch to an allowlist of theme files (style.css, *.php, inc/, template-parts/, assets/, vendor/), or at least exclude LexiFlow/, .env*, *.properties, *.jks and *.keystore. Its 'dist/assets/*.map' and '*.log' patterns never match, and '.git' also drops .gitignore.
- If the backend image is built with the classic (non-BuildKit) builder, backend/Dockerfile.dockerignore is ignored and backend/.env enters the build-stage context. It still does not reach the runtime image. Add a LexiFlow/.dockerignore as well.
- WordPress theme: template-parts/about.php:23 echoes wp_get_attachment_image_url unescaped (use esc_url), and header.php echoes get_bloginfo('name') unescaped (use esc_html). get_template_part('template-parts/icons/' . $icon) relies on Carbon select-field validation; allowlist icon names before building the path.

**Notification actions and lock-screen questions** (`h-ipc`)
- The lexiflow:// VIEW intent-filter on the exported MainActivity has no internal consumer: shortcuts.xml, notification openIntent and the widget all use explicit components. Any foreground app can still fire lexiflow://lockquestion/new to create questions, bump lockQuestionCounter/lastLockQuestionAt, and use up the daily lock-question cap (LockScreenRepository.kt:71-119; Daos.kt:293). Remove the implicit filter, or make the 'new' route require a user tap before createQuestion.
- NotificationHelper.kt:40 sets the channel lockscreenVisibility to VISIBILITY_PUBLIC. It does not override a per-notification PRIVATE request and gives no extra protection; drop it so the channel defaults to no override.
- LockScreenRepository.selfRate (lines 191-199) does not check that the question was answered correctly or rated only once, and isDue followed by answer is not atomic, so two concurrent RATE broadcasts could write two FSRS reviews. Gate it with an atomic 'rated' column and require outcome CORRECT. This is a same-user effect only.
- The question and result notification PendingIntents are FLAG_UPDATE_CURRENT, not FLAG_ONE_SHOT, and are not cancelled after use. Answers are protected by the atomic markAnswered, but explicit cancellation or ONE_SHOT would close stale-action windows for RATE.
- word_widget_info.xml declares widgetCategory keyguard, so the lemma and meaning can be revealed from a lock-screen widget on supporting devices. It shows no user-authored text.

**Server-side scoring of attacker-controlled battle submissions** (`h2-eval`)
- BattleManager.finishRoom runs CompetitionRules.score for every submission while it holds the single global battle Mutex (BattleManager.kt:248-259). Every queue, submit, rejoin, report and disconnect operation for all players is serialized behind up to about 20 ms of CPU per finished room. That cost grows linearly with volume and requires sustained multi-account rooms, so it is not a superlinear finding. Computing the evaluations outside the lock (copy room.submissions under the lock, score, then re-acquire to publish) would remove this coupling.
- Several evaluator passes are O(matches*n): although_but's lazy scan, sentence_capital's substring/trimEnd per match, the article 'A' substring per match, removeOverlaps O(issues^2) and applyCorrections. They are safe only because of the 1500-char cap. Keep CompetitionRules.score's take(MAX_CHARS) and the submit length check. Any new server caller of SentenceEvaluator.evaluate, whose default sanitize cap is 4000, should enforce a similarly small cap or use a linear look-back (for example, track the previous token while iterating).

**Stored backend token and device transfer** (`h-secrets`)
- data_extraction_rules.xml: device-transfer includes the whole 'file' domain, so the plaintext JWT DataStore (files/datastore/settings.preferences_pb) moves to the new device. Add <exclude domain="file" path="datastore/settings.preferences_pb"/>, or clear serverToken on first run after restore, so the new device registers itself and one 90-day token is not valid on two devices.
- SettingsScreens.kt 'Bağlantıyı kaldır' (Disconnect) deletes the token only on the device. The server has no revoke call, so a copied, transferred or restored token stays valid until it expires after 90 days.
- network_security_config.xml allows cleartext for 10.0.2.2 in release builds. On a real device, 10.0.2.2 is an ordinary RFC1918 LAN address, so a user who enters http://10.0.2.2 sends the bearer token and ?token= WS URL unencrypted across the LAN. Limit the cleartext domain-config to debug builds (a debug-only res/xml override).
- BackendClient.battleSocketUrl places the JWT in the WSS query string (line 112). There is no client-side leak, but sending it as a header or a first message would keep it out of server and proxy access logs (the server-side logging part belongs to the peer BattleRoutes unit).
- SettingsRepository stores the JWT unencrypted in DataStore. If defense-in-depth against rooted or forensic reads is wanted, wrapping it with an Android Keystore key would help. It is not a boundary failure under the app sandbox.

**WordPress theme PHP/npm dependency resolution and packaging** (`h2-deps`)
- Commit composer.lock (or pin htmlburger/carbon-fields to an exact version) so the vendor/ tree packaged by build-theme.php is bound to a reviewed version. Today ^3.6 resolves to whatever Packagist serves at build time. Also guard functions.php:9 with file_exists() so a missing vendor/ fails cleanly instead of fataling the site.
- build-theme.php: replace the strpos substring denylist with an explicit allowlist of theme files (style.css, *.php, inc/, template-parts/, vendor/, assets/) or build from `git archive HEAD`. The glob patterns 'dist/assets/*.map' and '*.log' currently never match. getRealPath() on a symlinked file resolves outside __DIR__, which corrupts the relative name and pulls outside content into the zip. A prior meimei-eco.zip in the tree is re-included.
- package-lock.json pins dev tooling with published advisories, all local-only with no attacker-controlled input in this repository: vite 5.4.10 (dev-server server.fs.deny bypasses, e.g. CVE-2025-30208/31125/31486/32395; vite.config.ts sets no server.host so the dev server stays on localhost), nanoid 3.3.7 (CVE-2024-55565), cross-spawn 7.0.3 (CVE-2024-21538 ReDoS), @babel/helpers 7.26.0 (CVE-2025-27789), brace-expansion 1.1.11 (ReDoS). Run `npm update`/`npm audit fix` to refresh them.
- functions.php:31 enqueues assets/js/main.js, which does not exist in the repository. If an assets/ directory is later generated outside source review, it would be packaged and served unreviewed. Generate it from a locked build or commit it.

### Positive source patterns

- JWT verifier pins HMAC256, issuer, audience, required `name` claim and expiry, and re-checks that the subject exists (local tests rejected alg:none, HS512, wrong key/aud/iss, expired, future-nbf, unknown sub).
- Battle protocol: per-message membership checks, single Mutex for deadline/submit/finish, idempotent result persistence, server-side scoring, frame-size and per-socket rate limits.
- Body readers cap declared and chunked bodies before decoding (413); WebSocket frames capped at 16 KiB including fragments.
- SQL fully parameterised; leaderboard `mode` is an enum.
- AI: static system prompts, single user-role message, typed decoding + shape validation on server and device, plain-Compose-Text rendering only (no WebView/HTML/intent sinks).
- Android: receivers/widget not exported; explicit PendingIntents (immutable except the RemoteInput reply); backup disabled; cleartext limited to local hosts; token cleared when the backend URL changes.
- `.apkg` import keeps only fixed entry names (no zip-slip); docker-compose runs read-only, cap_drop ALL, non-root, DB not published.
